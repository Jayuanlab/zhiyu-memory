# 现有服务兼容与实施边界

在制定改造卡、编写来源适配器或执行真实验收前阅读本参考。这里描述当前 Zhiyu Memory 的实现约束，不替代目标服务的能力发现。源码不可访问时，以认证后的 capabilities、宿主契约和实际测试为准；无法确认的能力记为缺项。

## 先识别服务模式

首次真实请求使用目标项目身份调用 `GET /v1/capabilities`，核对预期 namespace、模式、来源、策略、消费者和检索能力。能力响应不枚举全部权限或允许的 scope。

| 模式 | 可用接口和实施方式 |
| --- | --- |
| 标准 R/K/U | capabilities 含 `namespace`、`sources`、`policy`、`consumers`、`retrieval`；按已安装能力使用标准接口 |
| 已安装项目 | capabilities 的 `protocol` 为 `general-memory.project.http.v1`，含顶层 `tenantId/projectId` 和 `project`；仅调用宿主声明的 `/v1/project/call` operation |

已安装项目请求为 `{ "operation": "宿主声明的操作名", "input": {} }`。不能猜测 `propose`、`recall` 等 operation，也不能假定标准 facet 同时可用；当前安装模式的标准接口返回 `facet_not_installed`。安装模块由管理员在受保护环境中指定，HTTP 请求不能安装模块或任意调用函数。

标准模式常用边界：

| 层次 | 行为 | 不保证的内容 |
| --- | --- | --- |
| R 原始记录 | `/v1/records/commands` 保存 `observation.append`；query 精读和核对回执 | 不自动提炼 K，不自动注册来源，不参与长期知识向量召回 |
| K 长期知识 | `/v1/commands` 提案、审核、修订、退役；read/evidence/recall | 提交成功不等于审核通过；历史回执不证明当前仍有效 |
| U 受控交付 | `/v1/use/prepare`、`dispatch`、`status`，交给登记消费者 | recall JSON 本身不授予出站使用权限；交付成功不证明业务执行成功 |

标准协议当前为 `general-memory.v1-draft`。具体 JSON 从已安装的调用 Skill、宿主契约或目标解析器取得，不按本参考拼造字段。

## 默认研发装配不是通用业务连接器

仓库默认入口装配研发示例：R 来源 `demo.build`、K 来源 `demo.document`、消费者 `demo.local-model`。K 来源读取示例文档表和来源授权表；默认策略 `demo-dev.memory.records` 对真实团队规则的 `team-rule` 分类提供长期候选，复查期限默认 90 天、最长 180 天。

这些名称和表结构不是可直接套到任意业务的正式接入约定：

- 当前 HTTP 没有通用“上传业务文档”“注册来源”“新建项目并授权”入口。
- 给 R 写一段正文，不会让同一段正文自动成为可引用的 `demo.document`。
- 给任意业务数据贴 `team-rule` 标签不能代替分类、业务确认和策略适配。
- 默认示例的 `currentStates` 为空；不能把旧观察记录解释为实时订单、库存或账户状态。
- 测试消费者确认收到 Pack，不等于已接入业务模型网关。

接入需要项目建设采集器、来源适配器、权限映射、业务策略、增量同步和消费者；历史批量导入也属于项目工程。可以复用标准记忆内核和存储端口，或实现显式 installed project 模块，按现有架构选择。

合成夹具或管理员测试表只用于隔离验收，不作为实际项目接入的默认实现。现有本机测试空间和其他项目的凭证不能自动复用到目标项目。

## 来源适配器必须满足的契约

标准 K 的每条 `KnowledgeSourceRef` 包含 `namespace/sourceId/id/version/range/quote`。`sourceId` 必须登记，namespace 必须与认证项目一致。服务会通过受信适配器重新读取来源，而不是信任客户端提交的正文或 `evidenceConfirmed` 声明。

实施前把下列能力写进改造卡，并为它们找到实际代码位置：

1. **稳定身份与可重读原文**：根据业务实体 ID 读取权威来源；正文包含实际用于提炼的依据，不能只保存摘要或无法回读的临时 URL。
2. **完整版本**：适配器返回能够识别来源内容与相关元数据变动的真实版本。不要猜 `v1`，也不要仅使用未随正文修改的业务状态字段。
3. **准确摘录**：`range.unit` 为 `unicode_code_points`，左闭右开；`quote` 必须等于 `Array.from(content).slice(start,end).join("")`，保留换行和 emoji。
4. **有效时间**：返回真实的 `asOf` 和适用的 `expiresAt`；未来时间、过期来源、过期知识不能视为可用依据。
5. **来源权限**：按当前身份和项目核验来源访问权；普通读取、回执核对、召回和最终使用都有权限边界，不能只在导入时检查一次。
6. **一致性与最终核验**：标准存储端口要求来源、授权和版本在相应事务核验期间保持有效，并保持必要锁到审计或准入提交。来源变更、撤权和到期应阻断旧知识。

普通 HTTP 抓取一次远端正文不能自然满足第 6 项。远端系统无法提供所需一致性时，明确设计受控快照、版本与授权机制，并说明保证范围；契约缺口未解决就不能宣称已实现当前权限下的最终核验。

知识内容同时要有适用条件、反例和审核责任。无可核验依据的隐性经验先形成访谈记录、已确认案例或受控文档，再提交候选；代码中的特判只能证明实现行为，业务含义仍可能待确认。

## 治理与隔离

普通提案通常产生 `candidate`，具备相应 `review` 权限的身份核验后才可成为 `verified` 并参与长期召回。智能体不能因为提交成功就报告“长期知识已生效”。审核身份按项目既定职责提供，不能为试点自行提升普通 Agent 权限。

当前标准修订会产生新候选并立即将旧条目标为 `superseded`；新版本仍需审核。改造方案应说明审核期间的业务处理方式。来源版本变更、撤权、到期和策略版本变化也可能让已审核知识不可用。

项目隔离依赖服务端认证绑定的 `tenantId + projectId`，并在持久化、来源访问和检索时落实。每个目标项目配置专属身份和权限；客户端的 `expectedNamespace` 只检查接错项目，不负责授予权限。`scope` 是项目内检索分类，不能代替项目隔离。

验收隔离应实际使用两个项目身份，检查读写、来源和检索不会越界；只修改 JSON 中的 projectId 不是有效隔离测试。宿主适配器若绕过服务直查业务库，仍须独立落实其业务权限。

## 真实调用前需要什么

由宿主提供服务地址、目标 namespace、有效凭证注入方式、允许的 scope、来源读取工具与登记 ID、业务策略和所需权限。仅当场景包含受控交付时，还需要登记消费者及当前任务的衔接方式。

调用 Skill 的项目 profile 可包含 `baseUrl`、`tokenEnv`、`expectedNamespace`、`mode`、`timeoutMs`；Token 值通过受保护环境或宿主认证工具注入，不写入 profile、命令行、代码、日志或记忆正文。使用宿主已有包装器时先核对其是否固定指向其他 namespace。

向量验收还需要 capabilities 声明确实启用 `vector` 或 `hybrid`、模型可用且维度匹配。没有 embedding 配置时显式语义请求会失败；不能把关键词结果称为向量结果。保留实际模式、改写问题、预期知识、无关候选及阈值结果作为证据，阈值按该模型和语料校准。

缺少配置时仍可完成项目评估、改造方案和离线适配测试。应明确报告“离线验证通过；真实服务尚未接通”及剩余缺项。发现本机端口可访问、复制一个 profile 或 mock 返回成功，都不足以报告目标项目已接通。

## 持续采集与结果不明

优先复用项目已有事件、消息队列和任务系统。若业务动作与待同步事件必须一同保存，在原业务数据库的同一事务内写入 outbox，再由后台工作者提交记忆请求；不要在原业务事务里等待记忆 HTTP 调用。仅在事务提交后发内存事件可能丢失，需在方案中明确保证范围。

工作者应保存稳定业务事件 ID、来源版本、稳定命令 ID、完整请求、处理状态和回执，区分重复投递、暂时故障、永久拒绝与结果不明。稳定 ID 的生成也要包含目标项目与操作语义，不能把不同来源版本错误合并。

- **R/K 网络结果不明**：先用原 `commandId` 查对应 receipt，或按服务契约使用同一 ID 和完全相同正文重放；不能盲目换新 ID 重做。
- **版本冲突**：读取当前状态再决定；修改正文属于新操作，使用新 ID，并保留与旧事件的关联。
- **权限或来源拒绝**：记录阻断原因，按业务流程修复；不能改 namespace、来源或标签绕过。
- **installed project 写操作结果不明**：核对模块定义的业务回执；标准传输审计不是业务提交的证明。
- **U dispatch 结果不明**：用原 credential、consumerId、purpose 查 `status`，核对接收端；不自动重发，也不另行 prepare 重复交付。

标准 U 在最终准入中重新核验知识、来源、版本、权限和期限并提交审计，之后调用消费者。准入提交和消费者业务动作不是一个跨库事务；已经交付的数据也不能靠后来撤权收回。installed project 的身份库与业务库同样没有分布式事务。不能声称跨库原子提交或仅靠 outbox 就实现端到端“恰好一次”。

试点应覆盖至少与场景相关的重复事件、响应丢失、来源更新或撤权、未审核知识不可见，并提供关闭采集与停止知识使用的回退方式。业务主记录仍由原系统负责，动态业务状态通过实时工具取得。

## 可用源码定位

以下是服务仓库内定位提示，不是已安装 Skill 的文件依赖；复制本 Skill 后，先定位实际服务源码或使用宿主契约：

- `apps/service/main.ts`、`apps/service/demo.ts`、`apps/service/installed.ts`：部署模式、装配、installed operation 和传输审计。
- `examples/memory-project/knowledge-project.ts`、`examples/memory-project/policy.ts`：固定研发来源、权限、完整版本和示例策略。
- `packages/memory/src/knowledge-contracts.ts`、`knowledge.ts`：来源端口、严格字段、审核、召回和最终准入。
- `packages/memory/src/semantic-search.ts`：授权后向量计算、阈值与缓存边界。
- `packages/memory-postgres/src/knowledge.ts`、`service-identity.ts`：namespace 限定存储、身份和事务授权。
- `docs/agent-guide.md`、`docs/installed-projects.md`：标准调用与宿主安装说明。
