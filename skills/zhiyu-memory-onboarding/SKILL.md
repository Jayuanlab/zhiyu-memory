# 知语记忆接入

把当前项目中的可复用业务知识，接入有来源、可更新、受项目权限约束的记忆流程。分析单位是业务场景和信息生命周期，模块与目录用于定位证据和改造位置。

## 选择任务范围

| 用户请求 | 执行范围 |
| --- | --- |
| 评估项目、找接入机会 | 读取项目，输出有证据的业务信息地图、机会清单和缺项；保持业务代码、数据库、服务配置不变 |
| 设计接入或改造方案 | 完成必要评估，设计接入点契约和可排期任务；按项目惯例保存方案 |
| 接入、改造或实施试点 | 完成必要评估和设计，选择或沿用一个场景，实际改造、运行相关测试并报告完成程度 |

已有授权覆盖后续工作时直接推进，不在每个阶段重复请求确认。未授权的外部变更、生产迁移或真实数据导入，先完成可审阅的本地方案和代码。仅请求评估或方案时不顺带实施。

首先确认当前项目位置、适用的项目指令、目标使用者和最需要改善的业务问题。优先从现有任务和项目资料取得答案；只对会改变接入选择、且证据无法确定的业务含义提问。尚无明确场景时，可建议一个来源可靠、复用频繁、改造范围小的试点，并说明选择依据。

## 评估与规划

评估时阅读 [references/assessment.md](references/assessment.md)。沿一两个关键业务流程逐步检查文档、入口、应用服务、事务、状态流转、事件与数据模型，记录准确的文件位置；不能仅凭目录名分配接入任务。项目资料或工具不可访问的部分标为未评估，不推断全项目覆盖。

区分已确认的业务规则、代码当前行为与待确认假设。按任务复用价值、来源可靠性、更新可追踪性和改造维护成本判断优先级。同一模块可以同时有长期知识、事件证据和实时查询。

规划时使用 [assets/integration-plan.template.md](assets/integration-plan.template.md) 的相关部分，按项目规模裁剪。每个推荐接入点都要回答：哪个任务会用、依据在哪里、何时产生、何时读取、谁能读写、谁审核、如何失效、改哪里、如何证明有效。将实时业务事实交给原系统查询工具，把知识召回与实时结果在任务中组合。

在选择接入路线或改代码前，阅读 [references/service-compatibility.md](references/service-compatibility.md)。核对目标服务的实际能力与当前项目权限，不把仓库示例配置、字段或研发分类策略当成目标项目配置。不能靠复制 profile、只换 scope 或随意添加标签来完成接入。

## 单场景实施

实施时阅读 [references/implementation.md](references/implementation.md)。保留项目语言和现有框架，优先复用已有事件、任务、事务与授权接口；在清晰的接缝处实现来源与采集 Adapter，避免让记忆协议散落到业务代码。

完成一个可验证的生命周期：真实业务事件或版本化资料 → 可重读且有权限的来源 → 知识候选 → 按既定权限审核 → 有效知识召回 → 来源变更、撤权或到期后阻断旧知识。源数据、原始记录和知识候选是不同对象，不能假定保存其中一个自动创建其他对象。

使用当前项目明确提供的身份、namespace、来源和 profile。客户端可使用已有认证工具或已安装的 `zhiyu-memory`；缺少运行 Skill 不影响评估与规划，实施中按实际接口补齐调用工具。将密钥留在宿主私有配置与子进程环境，不写入方案、测试产物、命令参数或知识正文。

无服务、来源或身份配置时，继续实现可独立验证的适配代码和契约测试，明确记录剩余接线工作。测试替身的通过只说明本地契约行为；不得声称已经连接实际服务、完成真实审核或验证真实向量召回。

## 验收与交付

先验证目标任务：用与知识原文不同的问法检索，检查回答是否有正确依据和适用条件；当前业务状态仍从实时接口取得。再检查与改造相关的来源变化、未审核候选、权限撤销、项目隔离、重复事件、交付失败和业务事务行为。需要可靠事件交付时，验收故障恢复与回补；不要用简单重复调用掩盖结果未知的写入。

交付包含：有证据的接入机会与取舍、选中场景的来源及生命周期契约、具体改造和剩余缺项、实际运行的检查及结果。可将这些合并成一份方案；不要为每个标题机械生成文件。评估不等于完成适配，本地模拟通过不等于服务联调通过，真实服务检索通过不等于业务效果已经改善。

明确本次完成级别：`已评估`、`已规划`、`本地实现已验证` 或 `实际服务联调已验证`，并给出支持该结论的文件、命令或回执。评估失败、缺乏来源或不适合接入同样是有效结论，不为完成任务而制造可记忆内容。
