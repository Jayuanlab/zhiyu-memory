# 项目评估与业务信息分类

## 从问题追踪到实现

先找用户希望智能体更好完成的实际任务。区分开发维护、客服、运营等使用者；同一个信息对不同任务的价值不同。任务不清时，用已有资料提出一两个候选场景，并保留假设，而非先扫描全部数据。

按需使用项目文件搜索、依赖清单、架构文档和现有工具，逐步追踪：

1. 用户或系统从哪里发起任务，谁需要利用历史知识。
2. 当前业务判断经过哪些应用服务、状态流转和事务。
3. 文档、数据库、外部接口和工单中，谁持有权威来源。
4. 信息什么时候创建、修订、审核、关闭、撤销或删除。
5. 已有授权、事件、异步任务和错误恢复能复用哪些部分。

优先追踪目标流程；通过模块地图标出其他模块的覆盖范围。大型仓库可分工调查相互独立的业务流程，但每个结论仍需可追溯证据。避免扫描依赖、构建产物、私有凭证和无关原始数据。数据库不可访问时可检查 schema、迁移和查询代码，不假称已观察线上数据。

## 证据强度

| 发现 | 能证明什么 | 后续处理 |
| --- | --- | --- |
| 指定版本的已确认业务规范 | 该规范明确记载的规则与适用范围 | 检查负责人、有效期、真实来源权限 |
| 服务代码和测试 | 当前实现的行为，以及测试覆盖的情形 | 标记为实现证据；业务含义不明确时提出确认问题 |
| 已完成复盘的工单 | 该案例中实际确认的原因和处理过程 | 提取适用条件和反例，避免泛化成所有情况 |
| 访谈、聊天或推测 | 可能的规则、经验或业务意图 | 先形成待确认记录；经负责方确认并建立可重读来源后再提案 |

记录项目内文件位置与必要行号、版本或稳定文档 ID。保持“已证实、推测、待确认”可区分；发现矛盾时展示矛盾及其影响，不静默选一个版本当真。

## 信息去向

| 信息 | 典型去向 | 设计理由 |
| --- | --- | --- |
| 已确认规则、操作规范、设计决策 | 版本化来源 + 审核后的长期知识 | 在不同任务间可重复使用，且可检查有效性 |
| 执行日志、操作记录、异常过程 | 原始事件证据；有复用价值时另行提炼案例 | 事件发生不等于结论已成立 |
| 当前状态、余额、库存、价格 | 原业务系统实时读取 | 快照或相似案例不能证明当前业务事实 |
| 个人信息、客户标识、访问密钥 | 按任务最小化字段；密钥不进入记忆 | 检索需要的是处理经验，不是无关原始身份数据 |
| 暂时无法核验的信息 | 待确认、补来源或暂缓 | 不能用模型归纳补造缺失依据 |

优先接入有明确使用问题、可靠来源、负责人和可处理变更的知识。以高／中／低说明复用价值与维护成本即可；只有有数据依据时才给精确分数、收益或工作量估算。

一个模块可以包含多个去向。不将“订单模块接入”直接翻译成订单表全部向量化；也不把业务主数据镜像当作完成知识治理。

## 接入点契约

每个选中场景按需要明确：

- **用途与读取**：使用者、具体问题、调用位置、输入上下文、召回范围、未命中或不可用时的处理、需要的实时查询。
- **来源与产生**：权威来源、稳定标识、真实版本、原文／摘录、时间与期限、负责方、写入触发、历史资料回补方式。
- **知识与治理**：提炼字段、适用条件、反例、分类策略、候选与审核身份、更新／冲突／到期／退役路径。
- **权限与隔离**：项目 namespace、成员操作权限、来源访问授权及其撤销。scope 仅为检索分类。
- **交付与运维**：既有事件机制、幂等键、稳定命令和回执、失败恢复与回补、吞吐与时延约束、回退方式。
- **实施与证据**：现有能力、需建设能力、文件或方法改动、依赖、验收问题和完成条件。

无权访问的资料不复制到更宽的检索空间。业务中的租户、组织、角色、客户归属未必等同于记忆项目 namespace，必须明确它们如何映射到来源授权；不能仅凭 projectId 假定所有项目成员都可读所有业务资料。

## 方案的可实施程度

方案应明确选择标准服务接入或宿主项目模块路线，并指出服务端是否还要更换示例来源、成员逻辑与分类策略。以小范围改造为起点，说明选择原因及扩展条件。

对每个任务写清“在哪里改、为什么改、依赖什么、怎样验收”。如果权威文档、业务审核人、服务身份或运行环境缺失，将它们作为明确的接线任务；不要把缺少这些信息的方案标为可直接上线。
